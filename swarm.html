Method

How we decide what to attack

The rules below are the ones we run on ourselves. They are the reason a client’s finding and our own change go through the same evidence bar.

  • R-01
    Scope before contact

    Every target is registered with a scope class — our own, a bounty we are paid for, a signed engagement, a competition, or a lab — before a single request is sent. A scoped target may never be used to reach an unscoped one. If the only path out of scope is the finding, that path is the finding and the work stops there.

  • R-02
    Availability is production

    No denial of service, no destruction, no wiping. Destructive effects are simulated instead of performed. The control is that the engagement delivers the hardening control and the detection, not that it breaks something.

  • R-03
    No finding without a reproduction

    If the attack path cannot be executed end to end against the target, it is not a finding. It is a hypothesis, and hypotheses do not go in the report. This is the rule that keeps false positives out of a client’s backlog.

  • R-04
    Every artefact is hashed and logged

    Tools, scripts and evidence are recorded with a hash and a timestamp. The client can reconstruct what was run, on what, and in what order.

  • R-05
    No unattended persistence on a client host

    Anything left behind for an engagement is listed, owned and removed on request. A security team that leaves persistence behind on purpose is a security team with a problem.

  • R-06
    Our own changes get the same gate

    The security gate that screens a client’s code screens ours. A change that trips an assertion is blocked and the tree is rolled back. We do not ask clients to trust a process we will not run on ourselves.
