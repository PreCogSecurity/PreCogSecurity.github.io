The honest question

Why not just point an LLM at your repo?

You are right to ask, and we should answer it before you ask it. A good model can read your code and describe a vulnerability. That is genuinely useful, it is fast, and it is not nothing.

A model on its own

  • Describes a plausible vulnerability in code it has read, without a running system to prove it against.
  • Cannot execute the attack path, so a theoretical issue and a live breach look identical in the output.
  • Cannot run your suite, so the fix it proposes is unproven against the code you actually ship.
  • Leaves you with prose. A paragraph about the fix is not a fix, and no detection is written to catch the next attempt.
  • Has no memory between runs, so the same regression is re-discovered every quarter at full price.

An autonomous team, with a gate

  • Executes the attack against your running system and keeps the raw request and response as evidence.
  • Refuses to report anything it could not reproduce — a finding is a proven path, not a suspicion.
  • Lands the patch in your repository as a diff, and runs your own test suite before it reaches you.
  • Writes the detection and proves it fires, because a fix without a detection is a fix that silently regresses.
  • Remembers. Every fix we ship is re-tested on a clock, so a regression is caught by us before an attacker catches it again.
We are an LLM shop. We are just not an LLM only. The models do the reading, the writing and the reasoning. What makes the difference is everything around them: the scope registry, the evidence requirement, the gate that blocks a bad diff, and the refusal to call something a finding until it has been proven. That machinery is the product, and it is the part you are buying.
Worked example

One finding, end to end

A redacted example from a real engagement class: a cross-tenant read in a multi-tenant API. This is the shape of every finding we ship. The report is one page — the other four artefacts are what make it worth paying for.

01 — ATTACK

We reach it

The object identifier is ours to change. We change it and watch what the service says.

# tenant A requests tenant B's order GET /api/v1/orders/9812 Authorization: Bearer <token_A> 200 OK { "id": 9812, "customer": "Beta Holdings", "total": 41200, "status": "shipped" }
02 — VERIFY

We prove it

One request, no retries, no race condition, no fluke. It returns another customer's data, every time.

# same token, foreign id, 10/10 200 foreign_id=9812 200 foreign_id=9813 ... 200 foreign_id=9821 # tenant check on the id: missing # /api/v1/orders/{id} never compares # owner_id against the session
03 — PATCH

We fix it

A diff against your code, in your repository, passing your own test suite. Not a paragraph about a diff.

- order = Order.objects.get(id=id) + order = get_object_or_404( + Order, + id=id, + tenant_id=request.tenant.id, + )
04 — DETECT

We make it visible

A fix without a detection is a fix that silently regresses. We ship the rule and prove it fires.

# detection: cross-tenant read attempt when (route == "/api/v1/orders/*" and status == 200 and order.tenant_id != session.tenant_id) alert("precog.idor.cross_tenant_read") block(response)
05 — PROVE

We close it

The regression test fails before the patch and passes after. Then we re-test it on every future cycle.

def test_cannot_read_other_tenant_order(client): r = client.get("/api/v1/orders/9812", headers={"Authorization": "Bearer A"}) assert r.status_code == 404 # before patch: 200 -> test fails # after patch: 404 -> test passes
That is the whole product. Not a dashboard, not a monthly PDF, not a severity score. A proven path, a fix, a detection and a test — and the evidence for all four, in your repository, where your team owns it.

How an engagement runs

Six steps, and none of them is "write a report"

The same pipeline every time, whether the engagement is a $500 audit or a continuous engagement. You always know which step you are in.

01 — SCOPE

Written rules of engagement

What we may touch, what we will not, and how we contact you if something unexpected happens. Agreed in writing before a single request is sent.

02 — ATTACK

Adversary emulation

Chained techniques executed against your running system, using the paths a real attacker would take — not a signature checklist against a copy.

03 — VERIFY

Reproduce or discard

Every candidate finding is executed end to end. If the path does not work, it is not a finding — it is discarded, and it does not reach your dashboard.

04 — FIX

The patch, in your repository

The fix lands as a diff against your code, in a branch you control, and is run against your own test suite before you ever see it.

05 — DETECT

The rule that catches it

For every technique that landed, a detection is written and tested against real activity. We do not close a finding until the rule fires.

06 — PROVE

Regression test and retest

A test that fails before the fix and passes after it, plus a re-test of every fix we have shipped, so nothing quietly comes back.

Before you ask

Straight answers

Do you need access to our source code?

No. Black box testing against the running application is the default, and it is the more honest test. If white box access would produce a materially better result we will say so and scope it separately — we do not quietly ask for credentials we do not need.

Will you disrupt our production?

No. Availability is treated as a production dependency, not a test resource. No denial of service, no destructive action, no wiping. Where an engagement needs a destructive effect we simulate it instead, and we agree the rules of engagement with you in writing first.

What do we get at the end?

A report a CTO can act on: an executive summary, the findings with exact paths and working exploits, the fixes as diffs with regression tests, and the detections that would have caught the activity. Plus the raw evidence, so anyone on your side can reproduce every claim.

Why not just point an LLM at our codebase?

Because a model can describe a vulnerability but cannot prove the attack path works, cannot run your test suite, cannot write the detection, and cannot remember what it fixed last quarter. The full answer is here.

What happens if you find nothing?

You get a clean report that says exactly what was tested, how it was tested, and what was out of scope. That document is evidence of coverage, it is yours to keep, and it is more useful than a long list of theoretical issues.

How fast can you start?

The free scan is scoped within 48 hours of your request. Engagement start dates depend on scope, and we will tell you the real date rather than a hopeful one.

Do you train models on our code or our data?

No. What you send is used only to test the target you named, for your engagement. It is never used to train a model and never shared with a third party. We will put that in the engagement letter.

Can you keep our findings confidential?

Yes. Disclosing to the vendor is the default because it is what actually gets you fixed, but confidentiality is the norm and coordinated disclosure is standard practice — we do not publish a finding before the responsible party has had a fair chance to fix it.
